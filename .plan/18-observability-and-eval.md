## 目标

两件事，性质不同：

| 部分     | 回答什么问题                                        |
| -------- | --------------------------------------------------- |
| 可观测性 | 系统在做什么？慢在哪？为什么报错？                  |
| LLM 评测 | AI 的回答**好不好**？改了提示词是变好了还是变差了？ |

第二部分是 AI 应用特有的，也是最容易被跳过的。**跳过它，你就无法回答面试官的"你怎么知道你的 RAG 效果好"**，只能说"感觉还行"。

## 第一部分：可观测性

### 日志

用 `pino` + `nestjs-pino`。选它的理由：结构化 JSON 输出、性能好、生态成熟。

| 包            | 版本   | 用途                          |
| ------------- | ------ | ----------------------------- |
| `pino`        | 10.3.x | 结构化日志核心                |
| `nestjs-pino` | 4.6.x  | NestJS 集成、pino-http 中间件 |
| `pino-pretty` | 13.1.x | 开发环境可读输出（dev 依赖）  |

| 环境        | 输出                                |
| ----------- | ----------------------------------- |
| 开发        | `pino-pretty` 彩色可读              |
| 生产/打包版 | JSON 写文件（Tauri 的应用日志目录） |

**日志的安全约束**（`.cursor/rules/80` 已规定）：不打印完整的用户输入、文件内容、模型完整响应。需要排查时打印长度、哈希、前 100 字符。

理由：日志文件可能被分享（贴到 issue 里、发给别人排查），完整记录用户内容是隐私风险。

### 请求追踪

每个请求生成 `traceId`，贯穿整条链路：

```
HTTP 请求 (traceId=abc)
  └─ ChatService.stream
       ├─ VectorStore.search      [traceId=abc, 耗时 45ms]
       ├─ LlmGateway.embed        [traceId=abc, 耗时 320ms]
       └─ LlmGateway.stream       [traceId=abc, 首token 1.2s, 总 8.4s, 输出 156 token]
```

实现用 NestJS 的中间件 + `AsyncLocalStorage` 传递上下文，不用每层手动传 traceId。

SSE 响应头把 traceId 返回给前端，出问题时用户能提供它，你直接搜日志。

### LLM 调用指标

每次模型调用都记录：

| 字段                            | 用途                                |
| ------------------------------- | ----------------------------------- |
| model                           | 哪个模型                            |
| promptTokens / completionTokens | 上下文用量，判断是否接近上限        |
| firstTokenMs                    | 首 token 延迟（用户感知的"卡不卡"） |
| totalMs                         | 总耗时                              |
| tokensPerSecond                 | 吞吐                                |
| finishReason                    | 正常结束 / 达到长度上限 / 被取消    |
| toolCallCount / toolCallValid   | 工具调用次数与合法率                |

`finishReason == 'length'` 是个重要信号：说明输出被 `numPredict` 截断了。**如果这个比例很高，就是配置问题不是模型问题**——这正是当前代码里 `numPredict: 128` 会造成的现象。

### 开发期的调试面板

一个 `/dev/observability` 页面（仅开发环境），展示：

- 最近 50 次 LLM 调用的指标表格
- 上下文用量的分布（有多少次接近上限）
- `finishReason` 分布
- 各阶段耗时的火焰图式展示（检索 / 向量化 / 生成）

**这个页面的价值**：调优时能立刻看到"改了 chunk size 后检索耗时变化多少、上下文用量变化多少"。没有它就只能靠猜。

### 前端错误上报

不接 Sentry（本地项目，没有上报目标）。改为：

- 全局 ErrorBoundary，捕获后展示可操作的错误页（带"复制错误详情"按钮）
- 错误详情写入本地日志（走 platform 的 KV 或文件）
- 开发环境同时打印到控制台

### 不做什么

| 不做                   | 理由                                         |
| ---------------------- | -------------------------------------------- |
| OpenTelemetry + Jaeger | 单体应用单进程，分布式追踪没有对象           |
| Prometheus + Grafana   | 为一个本地应用搭监控栈，投入产出比极低       |
| Sentry / 云端 APM      | 无上报目标                                   |
| LangSmith              | 需要联网与账号，且本项目不完全依赖 LangChain |

如果想体验这类工具，作为独立的学习任务，不要塞进这个项目。

## 第二部分：LLM 效果评测 ★

### 为什么必须有

AI 应用的迭代是"改提示词 → 感觉好了 → 改切分策略 → 感觉又不行了"的循环。**没有量化指标，你永远在原地打转，且无法判断某次改动是改进还是退化。**

### 评测集

手工构造，放 `scripts/rag-eval/datasets/`。

| 数据集     | 内容                                     | 规模  |
| ---------- | ---------------------------------------- | ----- |
| 检索评测集 | 问题 + 标注的正确文档/片段 id            | 30 条 |
| 问答评测集 | 问题 + 参考答案 + 该问题应该基于哪些片段 | 30 条 |
| 拒答评测集 | 知识库里**没有**答案的问题               | 15 条 |
| 注入攻击集 | 含提示词注入的问题与文档                 | 10 条 |

**拒答评测集最容易被忽略但很重要。** RAG 系统最危险的失败不是答不出，而是**编造**。测"该说不知道时能不能说不知道"，比测"能不能答对"更能体现工程严谨性。

30 条的规模足够看出趋势，且人工标注的成本可接受（一个下午）。

### 检索指标

| 指标           | 含义                            | 怎么算       |
| -------------- | ------------------------------- | ------------ |
| Recall@k       | 前 k 个结果里包含正确片段的比例 | 标注 vs 召回 |
| MRR            | 正确片段的排名倒数均值          | 衡量排序质量 |
| 命中率         | 至少召回一个正确片段的问题比例  | 最直观       |
| 平均相似度分数 | 用于校准阈值                    | —            |

这些是**客观指标，不需要 LLM 参与**，稳定可重复。优先做这部分。

### 生成质量指标

这里麻烦：评估生成质量需要"裁判"。

| 方案                                 | 评估                                                          |
| ------------------------------------ | ------------------------------------------------------------- |
| 人工打分                             | 最准，但 30 条 × 每次改动 = 很快就不想做了                    |
| LLM-as-judge（用 qwen3.5:2b 当裁判） | **不可靠**。2B 模型自己都不太行，让它评判自己的输出是循环论证 |
| **规则化指标**                       | 有限但客观。推荐                                              |

规则化指标清单：

| 指标         | 怎么算                             | 意义                 |
| ------------ | ---------------------------------- | -------------------- |
| 引用准确率   | 回答里引用的片段是否在检索结果中   | 检测编造引用         |
| 关键词覆盖率 | 参考答案的关键词在回答中出现的比例 | 粗略的正确性代理     |
| 拒答正确率   | 无答案问题中正确说"不知道"的比例   | **最重要的指标**     |
| 幻觉率       | 无答案问题中给出了具体答案的比例   | 拒答正确率的反面     |
| 注入抵抗率   | 注入攻击集中没有照做的比例         | 安全性               |
| 平均响应长度 | —                                  | 检测过度啰嗦或被截断 |

**人工打分只在版本对比时做**：改了策略后,人工看 10 条 A/B 对比,记录哪个更好。不做全量人工评分。

### 评测报告与趋势

每次评测输出 `scripts/rag-eval/reports/YYYY-MM-DD-HHmm-<变更说明>.md`，**提交入库**。

报告包含：配置快照（chunk size / topK / 阈值 / 模型 / 提示词版本）、各项指标、与上一次的对比（涨了还是跌了）。

配置快照非常重要。三个月后看到"Recall@3 从 0.6 涨到 0.75"，得知道当时改了什么。

### 用评测驱动优化

有了基线后，可以做有依据的实验：

| 实验                                  | 看哪个指标                               |
| ------------------------------------- | ---------------------------------------- |
| chunk size 300 vs 500 vs 800          | Recall@3、MRR                            |
| 有无 overlap                          | Recall@3                                 |
| 固定切分 vs 递归切分 vs Markdown 感知 | Recall@3                                 |
| 父子切分 vs 普通切分                  | Recall@3 + 回答质量                      |
| topK 3 vs 5 vs 8                      | 命中率 vs 幻觉率（k 越大越容易引入噪声） |
| 相似度阈值 0.2 vs 0.3 vs 0.4          | 命中率 vs 拒答正确率                     |
| 提示词 v1 vs v2                       | 拒答正确率、注入抵抗率                   |

**这张实验表就是简历上的素材。** "我通过评测发现 chunk size 从 500 降到 300 使 Recall@3 提升 12%，但 topK 超过 5 后幻觉率显著上升" —— 这种话是有说服力的。

## CR-14 · MCP 工具选择对比

CI 与单测不调用真实 Ollama，因此本批次**没有**编造新的工具选择正确率。依据 `.plan/04` 2026-08-26 基线：`qwen3.5:2b` 在 6 个工具时合法 JSON / 工具选择 / 参数正确率均为 1.0。MCP 工具合并后仍截断到 `capabilities().maxToolCount`（该模型为 6），未勾选的工具不会进入模型列表。若要补实测，应在 `pnpm baseline` 下分别跑「仅内置工具」与「内置 + toolFilter 后的 MCP」并写入 `scripts/model-baseline/reports/`。

## 风险与备选

| 风险                                         | 处置                                                                                                                            |
| -------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------- |
| 构造评测集很费时，容易半途放弃               | 从 10 条开始（每个数据集），跑通流水线后再扩到 30 条。**有 10 条的量化指标远好于 0 条**                                         |
| 评测指标全面但都不高，看着很挫败             | 这是真实水平。指标的价值在于**趋势**而非绝对值。README 里如实写明本地小模型 + 768 维中文 embedding 的能力边界，这是诚实且专业的 |
| 规则化指标（如关键词覆盖率）与人的判断不一致 | 承认它是代理指标。关键决策（是否采用某个策略）辅以 10 条人工 A/B                                                                |
| 想用 LLM-as-judge 但模型不够强               | 不做。用 2B 模型当裁判的结果没有参考价值，会误导优化方向                                                                        |
| 评测跑得慢（30 条 × 每条要调模型）           | 检索指标不需要生成，很快，优先跑。生成指标可以只在重要变更时跑                                                                  |
| 日志文件无限增长                             | pino 配 rotation，或简单地限制单文件大小 + 保留最近 N 个                                                                        |
