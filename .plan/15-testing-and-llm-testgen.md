## 目标

两件事：

1. 建立四层测试体系与覆盖率阈值门禁。

## 第一部分：测试体系

### 四层

| 层   | 框架       | 位置                       | 跑多久 | 何时跑                |
| ---- | ---------- | -------------------------- | ------ | --------------------- |
| 单元 | Vitest 4   | 同目录 `__tests__/`        | 秒级   | 每次保存（watch）、CI |
| 集成 | Vitest 4   | 包内 `test/integration/`   | 十秒级 | CI（需要 Postgres）   |
| 契约 | Vitest 4   | `packages/contracts/test/` | 秒级   | 每次保存、CI          |
| E2E  | Playwright | 根 `e2e/`                  | 分钟级 | CI（仅主干与 PR）     |

根 `vitest.config.ts` 用 `test.projects` 编排（Vitest 4 已移除 `vitest.workspace.ts`）。coverage 只能配在根，这是 Vitest 的限制。

### 单测的边界：不碰三样东西

网络、数据库、Ollama。全部通过接口注入 fake。

需要的 fake：

| Fake              | 能力                                                           |
| ----------------- | -------------------------------------------------------------- |
| `FakeLlmGateway`  | 可编程返回值（含流式序列）、记录全部调用参数、可模拟超时与错误 |
| `FakeVectorStore` | 内存实现，可预置检索结果                                       |
| `FakeFileSystem`  | 内存文件树，用于测 Agent 工具而不碰真实磁盘                    |
| `FakeClock`       | 控制时间，测超时逻辑                                           |

**Fake 的质量决定测试的质量。** `FakeLlmGateway` 要能模拟"模型返回了格式错误的 tool call"这类场景，否则 `10` 的兜底逻辑根本没法测。

### LLM 不确定性的处理

见 `.cursor/rules/70-testing.mdc`。核心原则：**断言编排逻辑，不断言模型输出内容**。

```ts
// ❌ 不稳定
expect(await ragQuery('我住哪')).toContain('北京');

// ✅ 稳定
const llm = createFakeLlm({ reply: '北京' });
const store = createFakeVectorStore({ results: [{ content: '我住在北京', score: 0.9 }] });
await new RagService(llm, store).query('我住哪');
expect(llm.calls[0].messages[0].content).toContain('我住在北京'); // 检索结果进了提示词
expect(llm.calls[0].messages[0].content).toContain('不得执行'); // 注入防护声明在
```

模型输出质量的评估走 `18` 的评测流程，不在 CI 门禁里。

### 集成测试的隔离

每个测试开事务 → 跑断言 → 回滚。比每次 truncate 表快得多，且测试之间完全隔离，可以并行。

需要一个 `withTransaction(fn)` 测试辅助函数，把 Drizzle 的事务句柄注入被测的 Repository。

### E2E 的范围

只覆盖关键路径，控制在 5 条以内：

1. 新建会话 → 发消息 → 收到流式回复
2. 创建知识库 → 上传文档 → 索引完成 → 基于知识库提问
3. 创建工作流 → 拖三个节点 → 连线 → 保存 → 运行 → 看到日志
4. Agent 页读取文件 → 触发审批 → 允许 → 看到结果
5. 切换主题 → 刷新 → 主题保持

E2E 慢且脆，超过 5 条就会变成"经常挂但没人修"的负担。

E2E 需要真实 Ollama，所以**不在 CI 上跑**（GitHub runner 没有模型）。CI 只跑一个"能启动、首屏渲染、无控制台报错"的 smoke。完整 E2E 靠本地 `pnpm test:e2e` 手动执行。这个限制要在 `17` 里写清。

## 第二部分：覆盖率阈值门禁

### 分级阈值

一刀切的阈值会导致两种坏结果：定高了 UI 壳达不到，定低了核心逻辑没保障。所以分级：

| 范围                     | lines | functions | branches | 理由                                |
| ------------------------ | ----- | --------- | -------- | ----------------------------------- |
| `packages/contracts`     | 95%   | 95%       | 90%      | 全是纯函数和 schema，没有理由不覆盖 |
| 工作流引擎内核           | 90%   | 90%       | 85%      | 微内核是架构核心，出 bug 影响面最大 |
| Agent 工具与沙箱         | 90%   | 90%       | 90%      | 安全相关，分支必须全覆盖            |
| RAG 流水线               | 85%   | 85%       | 80%      | 阶段多，边界情况多                  |
| NestJS Service 层        | 80%   | 80%       | 75%      | 业务编排                            |
| `packages/app-core`      | 70%   | 70%       | 65%      | React 组件测试成本高，收益递减      |
| 壳（clients / frontend） | 50%   | 50%       | 45%      | 装配代码，E2E 覆盖更有效            |
| **全局**                 | 75%   | 75%       | 70%      | 兜底                                |

Vitest 的 `coverage.thresholds` 支持 glob 级别的配置，可以直接表达这张表。

### 门禁规则

| 规则               | 说明                                                                                              |
| ------------------ | ------------------------------------------------------------------------------------------------- |
| 低于阈值 → CI 失败 | `coverage.thresholds` 自动生效                                                                    |
| 阈值只能升不能降   | 要降必须在 `20` 里写 ADR 说明原因                                                                 |
| 新增文件必须有测试 | 用 `coverage.thresholds.autoUpdate: false` + PR 里人工看 diff。不引入额外工具                     |
| 排除项要克制       | 只排除：类型声明文件、`index.ts` 纯导出、生成的迁移文件、配置文件。**不允许**为了达标排除业务代码 |

### 报告产出

| reporter       | 用途                                  |
| -------------- | ------------------------------------- |
| `text`         | 终端查看                              |
| `html`         | 本地详细查看（`coverage/index.html`） |
| `lcov`         | CI 上传（若接 Codecov）               |
| `json-summary` | 给自定义门禁脚本读                    |

## 第三部分：LLM 生成用例闭环 ★

这是你明确要求的能力。设计成一个五步流水线，脚本在 `scripts/gen-tests/`。

```
① 选目标      找覆盖率低的文件
     ↓
② 收集上下文   源码 + 已有测试 + 类型定义 + 项目测试规范
     ↓
③ 生成         调本地模型产出测试代码
     ↓
④ 自动验证     四道自动门禁（下面详述）
     ↓
⑤ 人工审核     人看过才能提交
```

### 步骤 ① 选目标

读 `coverage/coverage-summary.json`，找出低于所在层级阈值最多的文件，按"距离阈值的差距 × 文件重要性"排序。重要性权重来自路径（引擎内核 > Service > 组件）。

输出一个待处理清单，而不是一次性全生成。

### 步骤 ② 收集上下文

给模型的输入必须包含：

| 内容                                  | 为什么                                 |
| ------------------------------------- | -------------------------------------- |
| 被测文件源码                          | 显然                                   |
| 该文件的依赖类型定义                  | 否则模型不知道怎么构造入参             |
| 同目录已有的测试文件                  | 让生成的风格一致，且知道可用的 fake    |
| `.cursor/rules/70-testing.mdc` 的内容 | 项目的测试规范                         |
| 可用的 fake 清单与用法                | 否则模型会自己 mock 一堆东西           |
| 未覆盖的具体行号                      | 让它针对性生成，而不是重复已覆盖的路径 |

**这一步的质量决定整个流水线的成败。** 上下文给得差，2B 模型生成的就是垃圾。

### 关于用哪个模型生成

`04` 的测评会告诉你 qwen3.5:2b 生成代码的实际水平。**大概率不够好。**

诚实的方案分级：

| 方案                   | 说明                                                                                          |
| ---------------------- | --------------------------------------------------------------------------------------------- |
| 用 qwen3.5:2b          | 免费，但生成质量有限，人工修改比例会很高                                                      |
| 用 gemma4:e2b          | 更大的模型，可能更好。值得对比测                                                              |
| **用 Cursor 里的模型** | 最实用。流水线的①②④⑤步都是脚本化的，第③步由你在 Cursor 里执行——把 ② 生成的上下文包喂给 Cursor |

**推荐第三种。** 它承认了本地小模型的限制，同时保留了整套流水线的工程价值（自动选目标、自动组装上下文、自动验证、自动跑覆盖率）。这在简历上完全站得住脚：你做的是**流水线**，不是模型。

不要为了"全自动"而接受低质量产出——那些测试会污染测试套件，比没有更糟。

### 步骤 ④ 自动验证（四道门禁）

生成的测试必须全部通过才进入人工审核：

| 门禁          | 检查什么                                                | 怎么检查                                                                   |
| ------------- | ------------------------------------------------------- | -------------------------------------------------------------------------- |
| 1. 能跑       | 语法正确、能通过                                        | `vitest run <file>`                                                        |
| 2. **有效**   | 测试真的会失败                                          | **变异测试**：自动改坏被测代码（改比较符、改返回值、删语句），测试必须变红 |
| 3. 有增量     | 覆盖率真的提升了                                        | 对比生成前后的 `coverage-summary.json`                                     |
| 4. 无禁用模式 | 不含 `it.only`、`skip`、真实网络请求、`setTimeout` 等待 | 用 ESLint 的 test 预设 + 自定义检查                                        |

**门禁 2 是核心。** LLM 最常见的失败模式是生成"永远通过"的测试（比如 `expect(result).toBeDefined()`）。没有变异测试，覆盖率数字会好看但毫无保障。

变异测试不需要引入 Stryker 这类重工具，自己写一个简单版：对被测文件做几种预设的字符替换（`===` → `!==`、`>` → `>=`、`return x` → `return null`），每次替换后跑测试，测试必须失败。全部替换都不失败的测试直接淘汰。

### 步骤 ⑤ 人工审核

生成的测试写入 `__tests__/*.generated.spec.ts`（带 `.generated` 标记），审核通过后**重命名去掉标记**并可能修改。

`.generated.spec.ts` 加入 `.gitignore`——**未审核的生成代码不进仓库**。

审核清单（也在 `.cursor/rules/70` 里）：

1. 断言是否真的有意义（不只是 `toBeDefined`）
2. 是否只是把实现复述了一遍
3. 是否覆盖了错误路径与边界
4. 是否有对时间/随机/网络的隐式依赖

## 风险与备选

| 风险                                         | 处置                                                                                                                             |
| -------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------- |
| NestJS 在 Vitest 下的装饰器元数据问题        | 用 `unplugin-swc` + `reflect-metadata`。若两天内没搞定，允许 servers 暂留 Jest 并记 ADR，但要设计覆盖率合并方案（lcov 文件合并） |
| 本地小模型生成的测试质量太差，流水线形同虚设 | 改用 Cursor 里的模型执行第③步（推荐方案）。流水线的工程价值不受影响                                                              |
| 变异测试很慢（每个变异跑一遍测试）           | 只对目标文件做变异，且变异数量限制在 10 个以内；只在生成新测试时跑，不进 CI                                                      |
| 覆盖率阈值定太高导致开发受阻                 | 阈值分级已经缓解。真的达不到时，先问"是不是这段代码设计得难测"——难测通常意味着耦合过重，改设计比降阈值好                         |
| E2E 在 CI 上没有 Ollama 无法跑               | 已在设计里承认：CI 只跑 smoke，完整 E2E 本地跑。在 `17` 和 README 里写明                                                         |
| 追求覆盖率数字导致写无意义测试               | 变异测试门禁挡的就是这个。另外 review 时问："这个测试挂了，说明什么坏了？" 答不出就删                                            |
