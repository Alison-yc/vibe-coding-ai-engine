## 阶段一：前端 dmg + 可配置后端

### 配置调整

`src-tauri/tauri.conf.json` 现状与需要改的地方：

| 项               | 现状                           | 改为                      | 原因                                       |
| ---------------- | ------------------------------ | ------------------------- | ------------------------------------------ |
| `productName`    | `liangzui-ai-app`              | 保留或改中文显示名        | 显示在 Finder 与菜单栏                     |
| `identifier`     | `com.liangzui.liangzui-ai-app` | 保留                      | 系统唯一标识，不要随意改（改了等于新应用） |
| `bundle.targets` | `"all"`                        | `["dmg", "app"]`          | macOS 上 `all` 会尝试构建不需要的目标      |
| `security.csp`   | `null`                         | 显式策略                  | **必须改**，见下                           |
| `app.windows[0]` | 1000×800                       | 加 `minWidth`/`minHeight` | 工作流画布在小窗口下不可用                 |

### CSP 必须收紧

`csp: null` 等于关闭所有内容安全策略。模型输出会被渲染到页面上，这是实打实的 XSS 面。

需要允许的连接目标：用户配置的后端地址（动态，无法在编译期写死）。处置方式：

- `connect-src` 允许 `http://localhost:*` 与 `http://127.0.0.1:*`（本地后端场景够用）
- `script-src 'self'`，不允许 `unsafe-inline` / `unsafe-eval`
- `img-src 'self' data: blob:`（Markdown 里的图片）
- `style-src 'self' 'unsafe-inline'`（Tailwind 运行时注入需要）

**注意**：`unsafe-eval` 的排除可能与某些库冲突（比如某些代码高亮或模板引擎）。构建后要实测每个页面的控制台有没有 CSP 报错。

### 图标

`src-tauri/icons/` 现在是 Tauri 默认图标。替换步骤：准备一张 1024×1024 的 PNG，用 `pnpm tauri icon <path>` 一键生成全套尺寸。

### 首次启动引导

```

│  无法连接到后端服务                      │
│                                        │
│  请先在终端启动后端：                    │
│    cd <项目目录>                        │

└────────────────────────────────────────┘
```

这个页面决定了应用是"能用"还是"打开就是白屏的半成品"。

## 阶段二：sidecar

### 难点在哪

Tauri 的 sidecar 机制本身不难（`externalBin` 配置 + `plugin-shell` 启动）。难的是**把 NestJS 打成单个可执行文件**。

| 方案                                           | 评估                                                                                                         |
| ---------------------------------------------- | ------------------------------------------------------------------------------------------------------------ |
| `pkg`                                          | 已不再积极维护，对 Node 24 的支持**当前信息无法确认**，需实测                                                |
| Node 官方 SEA（Single Executable Application） | Node 20+ 内置。但对 NestJS 这类有大量动态 require 的应用，实测常有坑                                         |
| Bun 编译                                       | `bun build --compile` 效果好，但项目是 pnpm + Node，引入 Bun 只为打包值得商榷                                |
| 打包 Node runtime + 源码目录                   | 最笨但最可靠：把 `node` 二进制 + `dist/` + `node_modules` 一起塞进 app bundle，Rust 启动 `node dist/main.js` |

**建议先试最后一种。** 它体积大（几十 MB）但确定能work，不用赌工具链兼容性。体积对本地应用不敏感。

### 还要解决的问题

| 问题                 | 处置                                                                                                                                                                                                  |
| -------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 数据库怎么办？       | Postgres 没法塞进 app bundle。两个选项：① sidecar 只跑 NestJS，Postgres 仍需 Docker（那"双击即用"就没实现）；② 桌面端后端改用 SQLite + sqlite-vec。**后者是真正的解法，但等于重写数据层，要慎重评估** |
| 端口冲突             | 启动前探测端口占用，被占则自动换端口并告知前端                                                                                                                                                        |
| 进程生命周期         | 应用退出时必须杀掉 sidecar，否则残留进程占端口。要处理强制退出（`kill -9`）的情况                                                                                                                     |
| 日志                 | sidecar 的 stdout/stderr 要落到应用日志目录，否则出问题无从排查                                                                                                                                       |
| 首次启动的数据库迁移 | sidecar 启动时自动跑迁移                                                                                                                                                                              |

### 关于数据库的关键判断

阶段二真正的拦路虎不是打包 Node，而是 **Postgres 不能随应用分发**。

如果坚持"双击即用"，就必须让桌面端用 SQLite + `sqlite-vec`。这意味着数据层要支持两种后端——这是一个不小的架构改动，价值也确实存在（抽象出 `VectorStore` 接口的两个实现，是很好的设计能力体现）。

**决策建议**：阶段二先只做"NestJS sidecar + 仍连 Docker Postgres"。它把"进程管理"这个技术点做掉了，但不承诺"零依赖双击即用"。SQLite 双后端作为独立的、更后面的升级项，记进 `20` 的 ADR 待办。

理由：把两个有难度的事情（打包 Node + 重写数据层）绑在一起做，失败风险叠加。

## 风险与备选

| 风险                                                      | 处置                                                                                                             |
| --------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------- |
| CSP 收紧后某个库不工作                                    | 逐项排查控制台报错。若确实需要 `unsafe-eval`，记 ADR 说明是哪个库、为什么、有没有替代品。**不要**直接改回 `null` |
| 打包版行为与 dev 模式不一致（常见于路径、环境变量、路由） | 每次改完必须测打包版，不能只测 dev。路由用 hash 模式规避 file:// 问题                                            |
| dmg 体积过大（含 Rust 二进制 + 前端产物）                 | 阶段一应该在 10～20MB 量级。若异常大，检查是否误打包了 source map 或 dist 里的旧文件                             |
| 阶段二的 Node 打包方案全部失败                            | 退回阶段一交付。**这完全可以接受**——阶段一已经满足你原始需求里说的"可配置连接本地端口访问"                       |
| 阶段二把项目拖到无法收尾                                  | 设硬时间盒：阶段二超过 4 天没跑通就停止，写清现状并交付阶段一                                                    |
| Apple Silicon 与 Intel 双架构                             | 只构建当前机器架构（Apple Silicon）。通用二进制不是学习目标                                                      |
