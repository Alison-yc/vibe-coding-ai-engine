# AI-Engine 开发计划总索引

这里是项目的**唯一权威计划源**。写代码前先读对应的 plan，改方向先改 plan。

## 怎么用这套文档

1. 先读 `00`（要做什么、不做什么）和 `01`（整体架构），建立全局图像。两份已完成，不要回头改范围，除非先追加 ADR。
2. 看本文件的「当前执行点」，决定下一步是开发还是 CR。**不要仅按 plan 编号顺序机械执行。**
3. 打开 `19-roadmap-and-milestones.md` 对应 CR 批次，只做该批次列出的 plan 子阶段。
4. 每个批次完成 DoD 后先标记 `待 CR`，停止新增功能；CR 通过后才进入下一批次。
5. 任何与 plan 不符的技术决策，先在 `20-adr-and-risks.md` 追加一条 ADR，再动代码。

更新规则：

- 开始实现：`待开发` → `开发中`
- 实现和自检完成：`开发中` → `待 CR`
- CR 发现阻塞问题：`待 CR` → `CR 修复中`
- 修复后：`CR 修复中` → `待 CR`
- CR 通过：当前批次 → `已完成`，下一批次 → `待开发`
- 里程碑最后一个批次通过后，下一动作必须先写「执行 Mx 集成 Review」，不能直接进入下一里程碑

状态完整定义见 [19 · 怎么决定下一步](./19-roadmap-and-milestones.md#怎么决定下一步开发还是-review)。

### 可以直接这样指挥模型

- **开发**：`开始当前批次。先读当前执行点和 CR 边界，只实现本批次，完成自检后停在待 CR。`
- **代码审查**：`CR 当前批次。按该批次 Review 重点和 DoD 审查，不修改代码。`
- **修复审查问题**：`只修复当前 CR 的阻塞问题，验证后把状态恢复为待 CR，不进入下一批次。`
- **推进**：`当前 CR 已通过，更新进度并告诉我下一批次；不要开始开发。`
- **里程碑审查**：`执行当前里程碑集成 Review，检查跨模块链路和里程碑 DoD，不新增功能。`

如果用户明确指定了其他批次，以用户指令为准；但必须先确认它的前置 CR 已完成。

## 依赖关系（不要跳步）

下面表示功能依赖，不代表 CR 执行顺序。`12`、`14`～`18` 会按子阶段穿插执行，详见 `19`。

```
02 工程底座
 └─ 03 契约层
     ├─ 04 模型基线 ──┐
     └─ 05 数据层 ────┤
                      ├─ 06 RAG ── 07 对话页
                      ├─ 08 工作流后端 ── 09 工作流画布
                      └─ 10 Agent 工具 ── 11 MCP
                                          └─ 12 双端 ── 13 打包
```

`04` 是隐藏的关键路径：它的实测结论会反过来修改 `10` 的工具数量上限和 `08` 的节点设计。**在 04 完成前不要开工 10。**

## 阅读这套文档时的注意事项

- plan 编号是主题编号；**实际开发顺序与 Review 门禁只认 `19` 的 CR 批次**。
- `12`～`18` 的总状态可能仍是「进行中」，必须查看各文件顶部的子阶段状态。
- 文档里出现的所有版本号都是编写时 npm 上的实际最新版，安装时如有更新以 `pnpm outdated` 为准，但**跨大版本升级要先在 ADR 里评估**。
- 文档里的目录结构是目标态，当前仓库还没有这些目录，由 `02` 负责创建。
- 凡是标注「当前信息无法确认」的地方，表示需要实际动手验证后才能填，不要凭猜测补全。
