## 怎么用这份文档

每做一个有取舍的技术决策，追加一条 ADR。格式固定：**背景 → 选项 → 决策 → 理由 → 代价 → 状态**。

写 ADR 的判断标准：**如果三个月后的你会问"当初为什么这么做"，就该写一条。**

状态取值：`已采纳` / `待验证` / `已推翻` / `待决策`

## 已采纳的决策（本次规划阶段确定）

### ADR-001 · 用 pnpm workspace + Turborepo 做 monorepo

**背景**：已有 pnpm workspace，但无构建编排工具。

**选项**：① 只用 pnpm 脚本；② 加 Turborepo；③ 加 Nx。

**决策**：Turborepo 2.10.x，远端缓存关闭。

**理由**：目标态有 6 个包，任务间有依赖（typecheck 依赖上游 build），手写 pnpm 脚本会失控。Nx 功能更强但配置复杂度和心智负担对单人项目过重。

**代价**：多一层概念；`globalEnv` 配置不当会导致缓存给出错误结果。

**状态**：已采纳

### ADR-002 · 契约层用 zod schema 共享，不做代码生成

**背景**：需要前后端类型一致。

**选项**：① 手写 interface 共享；② OpenAPI → 代码生成（Dify/opencode 的做法）；③ tRPC；④ zod schema 共享。

**决策**：④。

**理由**：一份定义同时得到编译期类型与运行时校验，无生成链路要维护。tRPC 与 NestJS 的模块/DI 体系冲突。代码生成对单人项目投入产出比低（要维护生成时机、产物入库、CI 一致性校验）。

**代价**：schema 写起来比 interface 啰嗦；前端运行时校验有性能开销（生产环境高频接口跳过）。

**状态**：已采纳

### ADR-003 · 移除 CopilotKit，自研对话流式

**背景**：原计划技术栈含 CopilotKit。

**决策**：不使用，自己实现 SSE + event reducer。

**理由**：三点。① CopilotKit 主要面向云端大模型，与本地 2B 模型的适配情况未知；② 对话页的 SSE 链路是工作流运行态和 Agent 页的共用基础设施，用第三方 SDK 会限制这三处的一致性；③ 自己实现 part 级增量渲染、取消传播、终止事件处理，学到的东西远多于配置一个 SDK。

**代价**：开发量增加约 2～3 天。

**状态**：已采纳

### ADR-004 · ORM 用 Drizzle

**背景**：需要 pgvector 支持。

**选项**：Drizzle / Prisma 7 / TypeORM / 裸 pg。

**决策**：Drizzle。

**理由**：对 pgvector 有一等支持（`vector()` 列类型、`cosineDistance()`）；生成的 SQL 与代码几乎一一对应，学得到数据库本身；类型推导好。Prisma 的 vector 支持要走 `Unsupported` + raw query，而向量检索正是本项目最核心的查询。

**代价**：生态比 Prisma 小；NestJS 官方文档以 TypeORM 为例，要自己摸索集成。

**状态**：已采纳

### ADR-005 · Docker + pgvector 官方镜像

**背景**：本机未装 Docker 也未装 Postgres。

**选项**：① Postgres.app/homebrew + 手编译 pgvector；② Docker + `pgvector/pgvector` 镜像；③ SQLite + sqlite-vec 起步。

**决策**：②，镜像 tag 写死为 `pg17`。

**理由**：环境完全可复现，`docker-compose.yml` 入库后换机器一条命令恢复。Docker 本身是后端岗位的常见要求。手编译 pgvector 在版本升级时容易搞坏。

**代价**：需要学习 Docker 基础（约半天）；Docker Desktop 占资源。

**状态**：已采纳

### ADR-006 · Agent 的文件操作在 NestJS 服务端，不在 Rust 层

**背景**：项目有 Tauri Rust 层，直觉上"本地文件操作该用 Rust"。

**决策**：全部在 NestJS 用 Node `fs` 实现。Rust 层只做原生对话框、UI 偏好存储、sidecar 管理。

**理由**：① 工具执行必须与 LLM 循环同进程，否则每次 tool call 跨 IPC，延迟叠加；② 否则要维护 Rust 与 TS 两套工具实现；③ Web 端也需要这个功能，放 Rust 层 Web 端就没有了；④ opencode 的 Electron 桌面端也是这个架构（文件 mutation 在 server 进程，见其 `packages/core/src/tool/`）。

**代价**：Rust 层的存在感降低，"用了 Rust"的含量不如预期。

**状态**：已采纳

### ADR-007 · 工作流不做并行执行

**背景**：Dify 的图引擎支持并行分支。

**决策**：第一阶段只做串行 + 拓扑排序。

**理由**：Ollama 是单实例，两个 LLM 节点并行只会互相抢资源反而更慢；并行会引入变量池竞态问题；调试难度显著上升。

**代价**：多个 HTTP 节点无法并行（但本项目场景下不构成瓶颈）。

**状态**：已采纳。有真实需求时追加 ADR 升级。

### ADR-008 · code 节点用 WASM 沙箱（QuickJS）

**背景**：code 节点要执行用户提供的 JS，是全项目最大的代码执行风险点。

**选项**：`eval`/`new Function` / Node `vm` / `isolated-vm` / `quickjs-emscripten` / 子进程。

**决策**：`quickjs-emscripten`。

**理由**：Node 官方文档明确说明 `vm` **不是安全沙箱**，可以逃逸；`isolated-vm` 需要原生编译，安装易出问题；WASM 边界提供真正的隔离，且沙箱内没有 fs/net/process 可访问。

**代价**：不支持 Node API 与 npm 包（但 code 节点本就该只做纯数据变换）；WASM 加载有初始化开销。

**状态**：已采纳（2026-08-27）。已验证 WASM 加载、对象输入输出、3 秒执行超时、内存/栈/输出限制，以及 `require` / `process` 隔离。

### ADR-009 · ESLint 用 9.x 而非最新的 10.x

**背景**：npm 上 eslint 最新是 10.9.0。

**决策**：起步用 `eslint@9.39.5`（npm 的 `maintenance` tag 指向的版本）。

**理由**：`typescript-eslint@8.67.0` 的 peer 范围虽然包含 `^10.0.0`，但生态插件（`eslint-plugin-import-x`、`eslint-plugin-react-hooks` 等）对 ESLint 10 的适配深度参差不齐。单人项目不值得花时间踩这个坑。

**代价**：不是最新版。

**状态**：已采纳。列为待办：M2 之后评估升级 10.x。

### ADR-010 · `frontend/` 改造为独立浏览器版 Web 应用

**背景**：`frontend/` 只有一个孤立的 `package.json`（且因为 workspace glob 是 `frontend/*`，它实际不在 workspace 内）。

**选项**：① 删除，只保留 Tauri 桌面端；② 改造为浏览器 Web 应用，与 Tauri 共用业务代码。

**决策**：②，业务代码下沉到 `packages/app-core`，平台差异走 `packages/platform`。

**理由**：一套代码两个端能体现架构抽象能力，且 Web 端演示比 dmg 方便得多（面试时发个链接比让人装 dmg 现实）。

**代价**：工程量增加；需要维护平台适配层；ESLint 护栏必须到位否则架构会腐化。

**备选位置说明**：把 Web 端放 `clients/liangzui-ai-web` 语义上更统一（`clients` = 所有客户端），但为honor现有目录结构选择了 `frontend/liangzui-ai-web`。如果后期觉得 `clients` 与 `frontend` 并存令人困惑，可以做一次目录搬迁。

**状态**：已采纳

### ADR-011 · LLM 生成测试用例的第③步由 Cursor 执行，不用本地 2B 模型

**背景**：需求要求"LLM 生成用例 → 自动执行 → 覆盖率报告 → 阈值门禁"的闭环。

**决策**：流水线的①②④⑤步脚本化（选目标、组装上下文、四道门禁验证、人工审核），第③步（生成）在 Cursor 里用更强的模型执行。

**理由**：2B 模型生成的测试代码质量大概率不足，会产出"永远通过"的无效测试污染测试套件。整套流水线的工程价值（自动选目标、上下文组装、变异测试验证、覆盖率门禁）不依赖于用哪个模型生成。

**代价**：不是"全自动"。但比全自动产出垃圾要好。

**状态**：已采纳。`04` 完成后可用实测数据重新评估是否能用 gemma4:e2b 自动化。

### ADR-012 · 不接 OpenTelemetry / Prometheus / Sentry

**背景**：可观测性通常会用这些。

**决策**：只用 pino 结构化日志 + AsyncLocalStorage traceId + 自建 `/dev/observability` 面板。

**理由**：单体应用单进程，分布式追踪没有追踪对象；为本地应用搭 Prometheus+Grafana 投入产出比极低；Sentry 无上报目标。

**代价**：简历上少几个工具名。但堆工具名不如把日志与指标真正用于调优。

**状态**：已采纳

### ADR-013 · Agent 工具按当前输入确定性选取

**背景**：M4 已有 5 个文件工具，而 `qwen3.5:2b` 的实测上限是 6 个。增加日期、计算、UUID 与天气 MCP 后，继续按注册顺序截断会让后注册工具永远不可用；把全部工具交给模型又违反 `.plan/04` 的能力门禁。

**选项**：① 提高 `maxToolCount`；② 再调用一次 LLM 选择工具；③ 用户手动切换工具预设；④ 根据当前输入关键词确定性选取相关工具，再按固定顺序补足文件工具。

**决策**：采用④。天气、日期、计算、UUID 与文件操作的意图词只负责决定候选集，不执行权限判断；实际工具仍由模型选择并经过 schema、权限与审批。文件工具只有在请求级 `fileAccess=true` 时才能进入候选，关闭时即使模型伪造调用也必须由执行面拒绝。对参数过多的 MCP 工具，配置可通过 `toolFilter.inputParams` 投影模型可见 schema，执行面同步拒绝投影外参数。

**理由**：不增加模型调用与延迟，结果可预测、可单测；保留原文件助手默认行为，同时确保新增工具能进入最多 6 个候选。实测依据是 2026-08-26 基线中 6 工具全指标 1.0，见 ADR-D01。

**代价**：隐含表达可能漏选工具；关键词需随真实用例维护。若后续工具类别继续增长，应升级为 UI 预设或独立轻量分类器，不能无限扩充关键词。

**状态**：已采纳（2026-08-28）

### ADR-014 · 统一对话入口与请求级文件访问

**背景**：现有 `/chat` 负责流式/RAG，`/agent` 负责文件工具与 MCP，导致日期、计算、天气只能在“文件助手”页面使用，同一用户还要维护两套会话入口。两条链路已经共用 `chat_sessions`、`chat_messages` 与 `MessagePart`，产品层继续分页没有必要。

**选项**：① 保持双页面；② 所有会话始终暴露全部工具；③ 统一为 `/chat`，实用工具按输入自动选择，文件能力由每轮请求显式开启。

**决策**：采用③。`POST /chat/sessions/:id/stream` 是主入口；日期、计算、UUID、实时天气按当前输入确定性进入工具链，不要求用户切换模式。文件访问由请求级 `fileAccess` 控制，同一会话可逐轮开关，刷新后默认关闭；开启时必须同时提供工作区，并继续经过路径沙箱、权限规则与审批。首批不在同一轮组合知识库检索与工具循环：实用工具意图或文件访问轮次跳过 RAG，并向前端发明确提示。旧 `/agent` 端点和 `agentType` 只作迁移兼容。

**理由**：统一会话历史与 UI，同时维持最小权限；按轮次门控不会把高权限状态静默带到下一次打开。工具轮次与 RAG 暂时互斥，避免在 `.plan/04` 未实测的“检索上下文 + 多工具”组合上假设 2B 模型能力。

**代价**：纯对话继续真流式，工具轮次仍受当前非流式 `agentChat` 限制；旧会话类型要兼容一段时间。未来若要同轮组合 RAG 与工具，必须先补真实模型基线与上下文预算验证。

**状态**：已采纳（2026-08-28）

### ADR-015 · 对话模型目录：已测评白名单 + 保守扫描

**背景**：会话存了 `modelId`，但 UI 不能改，网关请求写死 `OLLAMA_MODEL`。用户希望本机两个对话模型（`qwen3.5:2b`、`gemma4:e2b`）可切换，同时扫描 Ollama 已安装的其他 tag。

**选项**：① 仅白名单两模型；② `/api/tags` 任意模型完整 Agent；③ 已测评模型按 `capabilities()` 开放功能，扫描到的未测评模型只允许纯对话（及服务端 RAG 检索 + 生成），禁止工具。

**决策**：采用③（产品上的 A + 保守 B）。Embedding 模型永不进对话选择器。

**无缝的含义**：切换不重启应用、下一轮即生效；功能集合可以不同（例如 Gemma 若 tool-call 未过门槛则无工具）。不是「每个模型都能开文件访问」。

**未知模型**：`capabilities()` 缺省视为 `supportsTools: false`、`maxToolCount: 0`。请求带 `fileAccess` 或将触发工具循环时返回明确错误。禁止把 `/api/tags` 的名字直接当已测评能力。

**网关**：所有生成路径使用会话/请求中的 `model`，不得忽略该字段继续走环境变量。

**状态**：已采纳（2026-08-28）。CR-Z1 报告 `2026-08-28-gemma-tool-call.md`：Gemma 在 A/C 达路线 A，`supportsTools = true`，`maxToolCount = 6`；未测 B/D/E/F，不外推 12 工具或嵌套参数。默认模型仍是 `qwen3.5:2b`。Gemma 与 Qwen 共用 `numCtx=8192`、`numPredict=2048`，不单独加高：重叠工具指标持平，Qwen 测评覆盖更全，Gemma 仅热吞吐更好且冷启动更慢。

### ADR-016 · 界面国际化：i18next + 设置页切换 + 壳层按最长文案定宽

**背景**：`00` 曾把「国际化多语言」列为范围外，产品只做中文。现需在设置页提供中 / 日 / 英界面，且切换后不能因文案长短撑破导航、按钮或卡片。`.cursor/rules/00` 原硬性禁令与本次范围冲突，必须先改 ADR 再改规则。

**选项**：

1. 自研字典 + `t()` 包装：无新依赖，但缺复数、插值约定与生态，后期必重写。
2. FormatJS / `react-intl`：ICU 一等公民，样板更多，Vite SPA 不是其主场。
3. Lingui：编译期提取，对现有大量中文硬编码迁移成本高。
4. **i18next + react-i18next**：React SPA 事实标准；资源打包进 `app-core`，不走 HTTP 拉文案（本地优先、无 CDN）。

**决策**：采用④。BCP 47 语言标签仅 `zh-CN` / `ja-JP` / `en-US`。默认 `zh-CN`，**不**用浏览器语言探测器做首次覆盖（避免日文系统用户被静默切走）。语言显示名用各语言自称（中文 / 日本語 / English），选项本身不翻译。

**UI 语言 ≠ 模型语言**：界面 locale 不改 Ollama 系统提示、不翻译模型输出、不翻译知识库原文、MCP 工具名与描述、文件路径。服务端错误码映射放在 CR-I18N-B；I18N-A 不改 NestJS。

**分层**：文案与 `t()` 只在 `packages/app-core`。`packages/ui` 继续无文案。`document.documentElement.lang` 与持久化走 `packages/platform`（`kv` + `applyUiLocale`），**禁止** `app-core` 直接写 `document` / `localStorage`。locale 枚举在 `packages/contracts` 用 zod 定义一次。

**布局**：壳层（导航、页标题一行、主按钮）以 **en-US 为最长文案基准** 定 `min-width` / `max-width` 与 `truncate`；中日文只允许更短或在既有高度内换行（标题最多两行 `line-clamp-2`）。禁止 `w-fit` / `w-max` 包可变翻译。三语必须 `dir=ltr`。

**代价**：新增运行时依赖；E2E 不能再只靠中文 heading；漏翻 key 会回退中文，必须用键集合测试拦住。

**状态**：已采纳（2026-08-28）。实施前不得写业务代码；批次见 `19` CR-I18N-A / CR-I18N-B。

### ADR-D01 · Agent 走标准 function calling 还是结构化输出驱动

**背景**：本地 2B 模型的工具调用可能不可用，会迫使 Agent 改用结构化输出解析。

**依赖**：`04` 的工具调用测评结论。

**判据**：tool call 合法率 > 80% 且 3 工具下选择正确率 > 70% → 路线 A（标准 function calling）；否则 → 路线 B（结构化输出 + 代码块解析）。

**决策**：路线 A。`qwen3.5:2b` 在 1/3/6/12 工具下合法 JSON 率与选择正确率均为 1.0（60 次采样），3 工具假阳性为 0。12 工具参数正确率 0.95。默认 `maxToolCount = 6`。出处：`scripts/model-baseline/reports/2026-08-26-baseline.md` 工具调用阶梯表。

**理由**：实测超过路线 A 门槛，且 6 工具全指标 1.0，不必为尚未出现的失败预先上降级解析器。

**代价**：仍要用 zod 校验参数；12 工具时参数正确率已开始下滑，Agent 默认不得超过 6 个工具。`gemma4:e2b` 仅 A/C/G 过门槛（2026-08-28），未测两步与嵌套，切换后同样遵守 `maxToolCount = 6`。

**状态**：已采纳（2026-08-26）

### ADR-D02 · 工作流执行是否真的用 LangGraph

**依赖**：`08` 实施步骤 3 完成后的评估。

**判据**：LangGraph 的状态通道设计与自建的 VariablePool 是否冲突。冲突则改为自写串行拓扑执行器（<200 行）。

**原则**：不为了"用上 LangGraph"而扭曲架构。

**决策**：采用自建串行拓扑执行器，不引入 `@langchain/langgraph`。

**理由**：运行期状态由只读 VariablePool、条件分支裁剪和 Drizzle 运行记录共同定义；LangGraph 的 state channel 与 checkpointer 会形成第二套状态和持久化抽象。当前仅需串行拓扑执行，自建实现更直接且便于保证新增节点时 engine 零改动。

**代价**：循环、并行和通用 checkpoint 能力需要未来自行实现；当前 CR 明确不包含这些能力。

**状态**：已关闭（2026-08-27）

### ADR-D03 · NestJS 是否从 Jest 迁到 Vitest

**依赖**：`02` 实施步骤 7 的实测（NestJS 装饰器元数据在 Vitest 下是否正常）。

**判据**：两天内用 `unplugin-swc` + `reflect-metadata` 搞不定则暂留 Jest，但需设计 lcov 覆盖率合并方案。

**状态**：已关闭（2026-08-26）。

**结论**：迁移到 Vitest。默认 esbuild 转换能运行测试，但实测不会生成 `design:paramtypes`；接入
`unplugin-swc` 后，元数据回归测试、Nest TestingModule 单测与 HTTP e2e 共 3 条均通过。服务端统一使用
Vitest，不保留 Jest 或覆盖率合并链路。

### ADR-D04 · 桌面端是否改用 SQLite + sqlite-vec 以实现"双击即用"

**依赖**：`13` 阶段二的决策。

**背景**：Postgres 无法随 app bundle 分发。要实现真正的零依赖桌面应用，必须让桌面端用嵌入式数据库。

**判据**：这是一个不小的架构改动（`VectorStore` 要有两个实现）。建议先只做"NestJS sidecar + 仍连 Docker Postgres"，把进程管理这个技术点做掉，SQLite 双后端作为独立的后续升级项。

**原则**：不把两个有难度的事（打包 Node + 重写数据层）绑在一起做。

**决策**：CR-17 只实现 NestJS sidecar，不改 SQLite。构建时把当前架构的 Node runtime、NestJS `dist`、Drizzle migrations 与 production `node_modules` 一并放入 app bundle；Rust 用 Tauri sidecar 启动并管理进程。PostgreSQL 与 Ollama 继续由用户本机提供。

**理由**：Node 官方 SEA 对 NestJS 动态依赖的兼容风险高，`pkg` 对 Node 24 的支持当前信息无法确认；运行时加生产依赖体积更大，但已真实打包并启动。保留 PostgreSQL 可避免在交付阶段同时重写业务数据库与向量存储。

**代价**：`.app` 体积约 302 MB；仍需 Docker PostgreSQL 与 Ollama，不能宣称完全零依赖。当前只构建 Apple Silicon，与 plan 13 的单架构边界一致。

**状态**：已采纳，CR-17 审查通过（2026-08-28）。

### ADR-D05 · 中文全文检索方案

**依赖**：`06` 完成基础向量检索后，评测数据显示是否需要混合检索。

**背景**：PostgreSQL 内置分词器不支持中文，pgvector 官方镜像里没有 `zhparser` / `pg_bigm`。

**候选**：① 换用带中文分词扩展的镜像（要自己构建）；② 应用层用 `nodejieba` 分词后写入 `tsvector` 列。

**决策**：当前不引入中文全文检索，保留 pgvector + 应用层关键词重排。若后续固定集
Recall@3 低于 0.5，再优先采用②，不引入自定义镜像。

**理由**：CR-S1 的 PostgreSQL 同环境实验中，默认 topK 5 的 Recall@k 为 0.7000，
topK 3 的 Recall@3 为 0.6333，均未触发风险 R4 的 `< 0.5` 门槛。引入 `nodejieba`、
额外 `tsvector` 列和双路召回会增加依赖、迁移与排序调参成本，现有数据不足以证明收益。

**证据**：
`scripts/rag-eval/reports/20260828-0527-postgres-baseline.md` 与
`scripts/rag-eval/reports/20260828-0531-top-k-3.md`。

**代价**：中文语义接近但向量表示较弱的查询仍可能漏召回；继续用固定评测集监控，
触发门槛后再重开本 ADR。

**状态**：已采纳（2026-08-28），当前选择“不引入”。
