## 排期总览

时间估算按**每周投入 20～25 小时**（业余时间）计算。如果是全职投入，除以 2.5。

| 里程碑 | 内容                         | 工期   | 累计    |
| ------ | ---------------------------- | ------ | ------- |
| M0     | 工程底座                     | 2 周   | 2 周    |
| M1     | 模型基线 + 数据层            | 1.5 周 | 3.5 周  |
| M2     | RAG + 对话页                 | 3 周   | 6.5 周  |
| M3     | 工作流引擎 + 画布            | 3.5 周 | 10 周   |
| M4     | Agent 工具 + MCP             | 3 周   | 13 周   |
| M5     | 双端 + dmg 打包              | 1.5 周 | 14.5 周 |
| 收尾   | 评测、文档、README、演示视频 | 1 周   | 15.5 周 |

**约 4 个月。** 这是诚实的估算，包含了踩坑和返工的时间。看到"两周做完一个 Dify"的说法不要信。

## 如果时间不够，砍什么

按砍的优先顺序（先砍上面的）：

| 顺序 | 砍什么                                                  | 影响                                                 |
| ---- | ------------------------------------------------------- | ---------------------------------------------------- |
| 1    | `13` 阶段二（sidecar）                                  | 无。阶段一已满足需求                                 |
| 2    | `11`（MCP）                                             | 少一个热点技术词                                     |
| 3    | 工作流节点从 8 个减到 6 个（砍 `code`、`http-request`） | 少了两个有技术含量的节点（沙箱、SSRF），可惜但可接受 |
| 4    | 混合检索、父子切分等 RAG 进阶                           | 评测报告里说明为未来优化方向                         |
| 5    | 四套主题减到两套                                        | 无实质影响                                           |
| 6    | E2E 从 5 条减到 2 条                                    | 可接受                                               |

**绝对不砍的**（砍了项目就失去价值）：

- 模型基线测评（`04`）
- 工作流的插件化架构（`08` 的微内核）
- Agent 的三层安全（`10`）
- RAG 评测体系（`18` 第二部分）
- 覆盖率门禁与安全扫描（`15` `16`）
- 契约层（`03`）

这些是"工程能力"的体现。功能少一点没关系，工程做扎实了才是差异化。

## 进度追踪

每周做一次：

1. 更新 `.plan/README.md` 的进度表
2. 记录本周遇到的技术决策 → 追加到 `20-adr-and-risks.md`
3. 如果某个 plan 的估算明显偏离，更新本文件的排期

不要写周报式的日志文档，那是给别人看的。ADR 和进度表就够了。
