## 怎么决定下一步：开发还是 Review

plan 编号表示**主题**，不是严格的执行队列。实际执行顺序以本文件的 CR 批次为准。

每次开始工作前按下面顺序判断：

1. `.plan/README.md` 的「当前执行点」是否标记为 `待开发`：只开发该 CR 批次，不顺手进入下一个批次。
2. 当前批次实现完成但尚未通过自身 DoD：继续开发或修复。
3. 当前批次 DoD 全部满足且状态为 `待 CR`：停止新增功能，执行代码审查。
4. CR 有阻塞问题：只修 review 发现的问题，然后重新 CR。
5. CR 通过：更新当前批次为 `已完成`，再进入下一批次。
6. 一个里程碑内的所有 CR 都完成：先做「里程碑集成 Review」，通过后才能进入下一个里程碑。

**禁止连续完成多个 CR 批次后统一 review。** 底层错误会扩散到后续模块，最终很难判断是哪一个批次引入的。

### 状态定义

| 状态        | 含义                   | 模型下一步        |
| ----------- | ---------------------- | ----------------- |
| `未开始`    | 前置 CR 尚未完成       | 不得开工          |
| `待开发`    | 前置满足，当前应执行   | 按批次范围开发    |
| `开发中`    | 实现或验证尚未完成     | 继续本批次        |
| `待 CR`     | DoD 已满足，尚未审查   | 停止开发，执行 CR |
| `CR 修复中` | review 有阻塞问题      | 只修 review 问题  |
| `已完成`    | CR 已通过              | 进入下一批次      |
| `已搁置`    | 主动取消，并已记录原因 | 跳过              |

### 三层 Review

1. **批次 CR**：每个 CR 批次完成后执行，检查代码、测试、规则和该批次 DoD。
2. **里程碑集成 Review**：M0～M5 结束时执行，检查跨模块链路和里程碑 DoD；不能替代批次 CR。
3. **专项门禁 Review**：`04`、`08` 核对实测与 ADR；`13-A` 核对可安装交付物。通过后再决定后续路线。

## 实施批次与 CR 门禁

一个 CR 通常控制在 1～3 天。可以包含同一目标下的多个 plan 子阶段，但必须拆成清晰提交，且有共同的验收边界。

### M0 · 工程底座

#### CR-01 · Monorepo 与测试运行器底座

- **包含**：`02` 全部；`15-A` 的 Vitest projects、基础 coverage、NestJS 测试框架实测。
- **不包含**：FakeLlmGateway、LLM 测试生成、变异测试、完整 E2E。
- **Review 重点**：workspace 边界、任务依赖、架构护栏、格式与测试命令是否真的会失败。
- **通过条件**：`02` DoD；最小 `pnpm test` / `typecheck` / `lint` 可运行；ADR-D03 有实测结论。

#### CR-02 · 契约层与平台接口地基

- **包含**：`03`；`12-A`（platform + 最小 Web/Tauri 壳）。
- **提交边界**：契约层与 platform 层分成两个提交。
- **Review 重点**：跨进程类型唯一来源、运行时校验、platform 是否泄漏 Tauri/Web 形状、两个壳是否只做装配。
- **通过条件**：`03` DoD；`12-A` 的接口、最小双端壳、Provider 与 ESLint 护栏完成；`pnpm dev:web` 可用。

#### CR-03 · 设计令牌底座

- **包含**：`14-A`；`15-C` 的 Playwright 配置与第一条主题/令牌页 smoke。
- **不包含**：为未来页面预造大量业务组件。
- **Review 重点**：语义令牌、跨包样式是否丢失、UI 包依赖洁癖。

#### CR-04 · 安全与 CI 门禁骨架

- **包含**：`16-A` 的规则自测/SCA/Gitleaks；`17-A` 的快速门禁、测试、构建、安全 job。
- **依赖**：CR-01～03。
- **Review 重点**：故意制造错误时门禁是否真的失败；CI 与本地命令是否一致。
- **不要求**：尚未存在功能的攻击测试；它们随 `06` / `08` / `10` 补。

#### M0 集成 Review

- `pnpm ci:local` 全绿。
- 六个包的依赖方向正确。
- contracts、platform、ui、app-core 的架构护栏实测有效。
- CI 在远端真实运行，不能只做 YAML 静态检查。
- 通过后才能进入 M1。

本地自检（2026-08-26）：`packages/` 六包依赖方向符合分层（contracts 仅 zod；tsconfig 无运行时依赖；platform/ui 不依赖业务包；app-core 依赖 contracts + platform + ui）。护栏由根 `eslint.config.js` 与 `packages/eslint-config/src/architecture-guards.spec.js` 实测。workflow 已扩大到 `feature/**` / `feat/**` / `fix/**` 并支持 `workflow_dispatch`。

阻塞修复：type-aware ESLint 必须在 workspace 包 `dist` 存在之后运行。干净 checkout 上先 lint 会把未解析的 `@ai-engine/*` 打成 error type（约 116 条 `no-unsafe-*`）。CI 与 `pnpm lint` 改为先 `typecheck`（`^build` 产出 `dist`）再 eslint。远端是否整条绿：push 后看 GitHub Actions。

## 如果时间不够，砍什么

按砍的优先顺序（先砍上面的）：

| 顺序 | 砍什么                                                  | 影响                                                 |
| ---- | ------------------------------------------------------- | ---------------------------------------------------- |
| 1    | `13` 阶段二（sidecar）                                  | 无。阶段一已满足需求                                 |
| 2    | `11`（MCP）                                             | 少一个热点技术词                                     |
| 3    | 工作流节点从 8 个减到 6 个（砍 `code`、`http-request`） | 少了两个有技术含量的节点（沙箱、SSRF），可惜但可接受 |
| 4    | 混合检索、父子切分等 RAG 进阶                           | 评测报告里说明为未来优化方向                         |
| 5    | 四套主题减到两套                                        | 无实质影响                                           |
| 6    | E2E 从 5 条减到 2 条                                    | 可接受                                               |

**绝对不砍的**（砍了项目就失去价值）：

- 模型基线测评（`04`）
- 工作流的插件化架构（`08` 的微内核）
- Agent 的三层安全（`10`）
- RAG 评测体系（`18` 第二部分）
- 覆盖率门禁与安全扫描（`15` `16`）
- 契约层（`03`）

这些是"工程能力"的体现。功能少一点没关系，工程做扎实了才是差异化。

## 进度追踪

每周做一次：

1. 更新 `.plan/README.md` 的进度表
2. 记录本周遇到的技术决策 → 追加到 `20-adr-and-risks.md`
3. 如果某个 plan 的估算明显偏离，更新本文件的排期

不要写周报式的日志文档，那是给别人看的。ADR 和进度表就够了。
